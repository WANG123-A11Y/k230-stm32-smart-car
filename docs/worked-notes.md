# 踩坑记录（K230 语音助手模块）

记录本人在语音模块开发中实际遇到并解决的问题，按"现象 → 定位 → 根因 → 修法"整理。

---

## 1. 识别结果永远是空字符串

**现象**：日志显示云端返回了 JSON，但本地解析总是失败，拿到的文本永远是空。

**定位**：抓包/打印原始字节发现两件事叠加——① 该固件的 `socket.recv` 会**提前返回**，
响应没收完就结束了；② 云端响应是 **chunked 分块传输**，结尾挂着 `0\r\n\r\n` 帧标记。

**修法**：按 `Content-Length` 循环收满，再解 chunked 帧，之后第一次看到真正的识别文本。

---

## 2. 录音回放像"快进"，识别必失败

**现象**：录下来的声音回放到电脑上一听，语速快得像快进，识别自然全错。

**定位**：实测该固件**忽略请求的采样率**——请求 16 kHz，实际按 44.1 kHz 采集，
声音整体被"压缩"了约 2.7 倍。中途还试过用计时反推真实采样率，但会被线程调度干扰
（曾误测成 25491 Hz 导致变调），不可靠。

**修法**：改成"查表采信"——请求 44.1 kHz 并实测确认，然后在代码里线性降采样到 16 kHz 上传。
改完后"开始"两个字立刻识别正确。

---

## 3. 麦克风打不开：`kd_mpi_ai_enable_chn failed: -1`

**现象**：IDE 中断后软重启，再次打开音频通道报 `-1`，语音彻底不可用。

**根因**：音频通道被 IDE 中断过程占用未释放。

**修法**：断电重启。正式演示采用**上电自运行**，避免 IDE 介入。（另：该固件里 `pyaudio`
没有 `initialize`、`array` 没有 `frombytes`，只能改用 `struct` 解析 16 bit PCM 字节。）

---

## 4. 说"加速"却同时命中"减速"

**现象**：词表曾写成不含逗号的字符串，导致按**单字**匹配——"速"字同时命中"加速/减速"。

**修法**：词表统一改为元组并增加整词匹配校验，再叠加冲突优先级（停 > 启 > 减 > 加）。

---

## 5. 嘈杂环境（答辩现场）误触发

**现象**：环境噪声大时 VAD 被误触发，或在有人说话时识别到无关内容。

**修法**：多道门限叠加——

| 手段 | 作用 |
|---|---|
| 底噪自适应 + 能量双阈值 | 判定"开口/停顿"，比固定阈值抗环境变化 |
| 句内有效语音占比门槛（20%） | 噪声毛刺构成的"句子"直接丢弃 |
| 信噪比双阈值（相对 + 绝对下限） | 过滤远处人声与含糊声 |
| 同指令 8 秒内说两次才下发 | 大幅降低偶发误触发 |
| 指令优先级 + 下发后冷却 1.2 s | 防回声/余音连发 |
| 物理按键兜底（按键对讲模式） | 演示时的确定性方案 |

## 6. 声音在右声道

板载麦克风是**双声道取右路**，直接取左路会得到静音。代码里做声道提取。

---

## 7. 视觉与语音抢 UART

语音线程与视觉线程共用同一根 UART2 下发帧。若不加锁，两个线程同时写会让 STM32 收到
半截帧。

**修法**：语音线程创建时分配一把锁，两线程写 UART 前统一加锁。

---

## 已知不足

- 云端方案**依赖网络**，且有一次识别约 1 秒的延迟；后续应补离线降级路径。
- 音频前端（降噪 / 回声抑制）未做工程化处理，强噪声场景仍靠门限硬扛。
